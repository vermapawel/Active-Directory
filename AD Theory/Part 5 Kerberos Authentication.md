**Kerberos**

It is an authentication key agreement protocol. It allows two entities to establish a shared secret key secretly. Its a Symmetric key Cryptography.

There are two types of Cryptography. Public Key Cryptography and Symmetric key Cryptography.

In Symmetric key Cryptography there is a shared secret key which is the same for both parties, and it is used to protect the message. For example to protect the confidentiality of the message, by encrypting the message so that no one is able to see the message. So that's confidentiality protection through encryption. 

We can protect the Integrity of the message by signing the message by message authentication schemes using secret keys

<img width="878" height="518" alt="image" src="https://github.com/user-attachments/assets/5d1ecc7f-b504-49bf-96a4-7aeebaace347" />

Now, in Kerberos, the entities are not authenticated by digital certificate. Instead, entities can rely on a centralized server which is Key Distribution Center (KDC). This KDC knows the secrets keys of all entities involved in the communication.

When a client, wants to communicate with a service (for example SMB or LDAP service), they can establish a secure channel and share a Key. But to share this key, the client will have to communicate with KDC multiple times to generate tickets. These tickets are encrypted with a bunch of different keys. 

So the system will work only if we have the central point of trust which is the KDC.

KDC has to know the secret keys for client and server. By using such knowledge, it is possible to establish ephemeral session keys that allows the client to authenticate the server. Ephemeral session is a key this is only used to protect that particular session. As soon the session is over, ephemeral session key expires.

So, if we compromise the KDC, entire system is compromised.

**Kerberos Components**

**1.Key Distribution Center (KDC)** :- It the core component of Kerberos that deals with initial authentication and with issuing of tickets. 

It is made up for two specific services. Each of these two services generates specific tickets. Tickets will be encrypted with specific keys.

**#) Authentication Server (AS)**

It authenticates the user. After verifying the user identity, it generates a Ticket Granting Ticket (TGT). This ticket can be exchanged for Serving Tickets.

**#) Ticket Granting Server (TGS).**

It uses the TGT generated by the Authentication Server to generate the Service Tickets. The service tickets allow users to access server resources.

Lets understand the Flow

**Phase 1** > Authentication with KDC. When authentication is down, a TGT will be generated. All the entities that have a valid TGT are authenticated in Kerberos. It does not mean that they have access to any service.

**Phase 2** > If they want to access any specific service, they need to exchange TGT to obtain a ticket for specific service. We call this ticket as Service Ticket (ST). Once we have this Service Ticket, then we can use this ST to authenticate for any service. 

So the 1st authentication happens with Kerberos. The 2nd authentication happens within the actual service itself.

When we have a TGT, we can use the TGT without putting the password every time. We can use TGT to issue many Service Tickets. As long the TGT is valid, we can get as many Service Tickets.

**3. Principals**

A Kerberos Principal is a unique identity to which Kerberos can assign tickets. There are three types of Principals

#1) User Principal:- It represents an individual user in the Kerberos realm. This is also know as User Principal Name (UPN)

<img width="677" height="171" alt="image" src="https://github.com/user-attachments/assets/8c86af91-bdbf-4f4e-8950-84dd417d8609" />

leo@hexdump.lab is the Kerberos Principal for user leo. It is our identifier.

#2) Service Principal:- Represents a service that requires authentication and authorization to be accessed. For example, SMB Service, SQL service, HTTP service, LDAP service.

<img width="843" height="228" alt="image" src="https://github.com/user-attachments/assets/d7313077-c296-4d1c-84e4-267f65ab3482" />

Services need to register proper Service Principal Names (SPNs) within Active Directory. Once the registration is done, Kerberos can issue ticket for that service.

#3) Host Principal:- It represents a computer in a Kerberos realm. 

Each principal has an associated Secret Key, which is used during the key agreement protocol to provide authentication.

<img width="528" height="218" alt="image" src="https://github.com/user-attachments/assets/b1b79783-e8a5-40de-8569-0efbd043df1c" />

KDC knows the secret key for each principal. By knowing this the KDC is able to establish a secure channel. 

The client only know its own key. A service only knows its own key. By communicating with KDC, they are able to establish a share key among them.

Principal follows a common name structure. 

primary/instance@REALM

**4. Ticket Granting Ticket (TGT)**
   
Its a Kerberos ticket that is used to issue Service Ticket (ST) through a Key Distribution Center (KDC). 

TGT is issued only after proper authentication with the Authentication Server. It is encrypted with the KDC secret key.

If TGT is issued before proper authentication, an attack known as AS-REP Roasting can be performed on Kerberos realm.

TGT contains various information such as User ID, TGS ID, TGS Session key, Expiration Time, Ticket Flags etc.

**5. Service Ticket (ST)**
   
A Service Ticket, also know as Ticket Granting Service (TGS) is a Kerberos ticket that allows an authenticated user to access a specific service or resource. 

It is issued by the KDC, and specifically by the Ticket Granting Server. Once you obtain a ST, you can present it to the target service. The ticket is created in such a way so that only the service can decrypt it with its own secret key and it is used to validate the identity of the user.

If the ST is valid, the user will be allowed to access the resource without entering the passwords.
