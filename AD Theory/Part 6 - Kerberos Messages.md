
Authentication Server and Ticket Granting Server forms a KDC

<img width="663" height="207" alt="image" src="https://github.com/user-attachments/assets/2cd50b95-fe06-4e77-a524-c7dba3ac9566" />

1st message is AS-REQ between Client and Authentication Server. Here client wants to enter into Kerberos realm and ask for a Ticket Granting Ticket (TGT).

Now, there are two places where authentication can happen. Either in 1st message AS-REQ where Authentication Server check for authentication. Or, in TGS-REQ message where authentication is done by Ticket Granting Service (TGS)

Lets assume that Authentication happened in 1st message, AS-REQ, by the Authentication Server. The Authentication Server generates TGT and some other data, and revert by AS-REP message.

Now the client extract TGS session key and sends to the Ticket Granting Server via message TGS-REG. So TGS-REG contains TGT and some other data. The Ticket Granting Server validates and generates a TGS-REP. The TGS-REP contains the Service Ticket (ST). 

Now, the client use the ST to prepare the AP-REQ which is the request to actually access the service. If Mutual Authentication is required, the Service will replay with AP-REP containing another proof of authentication. 

So in Mutual Authentication, the Service can authenticate the Client and Client can authenticate the Service.

Lets understand each messages

**1. AS-REQ + AS=REP**

This is the 1st request/response that is sent.

Purpose: Obtain a Ticket Granting Ticket (TGT)

Entities:
- Client
- AS/KDC (Authentication Server / Key Distribution Center)
  
Messages:
- AS-REQ (Authentication Service Request), Client -> AS
- AS-REP (Authentication Service Reply), AS -> Client

**AS-REQ (Authentication Service Request)** :- It contain the pre authentication data such as:-

1#) PA-PAC-REQUEST 

Specifies if the user wants to obtain a TGT that includes, PAC data (Privileged Attribute Certificate), containing authorization information like group memberships and user privileges.

2#) PA-ENC-TIMESTAMP

It contains a timestamp encrypted with the user's key. It is used to prove that the request comes from the legitimate user, and it is also used to prevent replay attacks.

So we cannot sent the same authentication message twice, later in the future because the time window will be changed. 

This is a protection against Reply Attacks. 

When the KDC/AS receives this timestamp, it uses the user's secret key to decrypt the timestamp. If the timestamp is within an *acceptable window of time*, authentication proceeds. Otherwise, it fails.

**AS-REP (Authentication Service Reply)**:- It is the response of AS-REQ. It contains:-

1#) The TGT (Ticket Granting Ticket) issued by the KDC/AS. The ticket is encrypted using the Kerberos Ticket Granting Service (krbtgt) account key also known as TGS secret key

2#) The Encrypted Part, which contains the TGS session key (most important) and other authentication details such as the TGS Name, the timestamp, and the lifetime of the TGS. It is encrypted using the client's long-term key derived from the machine. The client will decrypt the message to obtain the session key which he will use in next message to get a Service Ticket.

Please note that TGS secret key and TGS session key are different. TGS secret key is the long term secret key of KDC. TGS session key is only used to establish the current session between client and Kerberos.

**2. TGS-REQ + TGS-REP**

This is the second request/response that is sent.

Purpose: To obtain a Service Ticket (ST) using the previously obtained Ticket Granting Ticket (TGT) and TGS Session Key. This interaction happens with the Ticket Granting Service (TGS).

Entities involved:
- Client
- TGS/KDC
  
Messages:
- TGS-REQ (Ticket Granting Service Request), Client -> TGS
- TGS-REP (Ticket Granting Service Reply), TGS -> Client

**TGS-REQ (Ticket Granting Service Request)**:- It contains following

1#) TGT that was generated by the Authentication Server in the 1st exchange. 

2#) The Service Principal Name (SPN) of the requested service and the desired lifetime for the Service Ticket (ST)

3#) Authenticator Date which includes the userID and the Timestamp, encrypted with TGS Session Key

**TGS-REP (Ticket Granting Service Reply)**:- Once the TGS receives the message, if perform following operations:-

- Decrypts TGT with TGS secret.
- Reads TGS Session key from TGT
- Decrypts authenticator data with TGS Session Key
- Validates authenticator data with TGT data
- Prepares ST(Service Ticket) encrypted with service secret key.
- Encrypts (ServiceID + Service Session Key) with TGS Session key.

**3. AP-REQ + AP-REP**

This is the third request/response that is sent.

Purpose of this exchange is for a client to establish an authenticated session using a previously obtained Ticket Granting Service (TGS) with a specific service.

Entities involved:
- Client
- Service
  
Messages:
- AP-REQ (Authentication Request), Client -> Service
- AP-REP (Authentication Reply), Service -> Client

**AP-REQ (Authentication Request)**:- It contains following:-

1#) The service ticket (encrypted with service key)

2#) An authenticator (encrypted with service session key). It contains the data that service can use to authenticate the client. 

**AP-REP (Authentication Reply)** :- When the service receives the AP-REQ, it performs following actions

- Decrypts the service ticket in order to obtain the service session key
- Uses the service session key to decrypt the authenticator
- Validates the authenticator data

The AP-REP contains:

- Encrypted timestamp from the client AP-REQ
  
It is used to implement mutual authentication, that is, it allows clients to authenticate the service.

**Mutual Authentication**

When we talk about mutual authentication we're referring to the two sides of authentication:

1. The service authenticates the client
2. The client authenticates the service
   
The first side of authentication happens with the AP-REQ request.

The second side of authentication happens with the AP-REP, if the flag mutual-required was set in the AP-REQ message sent by the client.

**Lets recap**

**1st Flow:-**

<img width="800" height="203" alt="image" src="https://github.com/user-attachments/assets/1fec6a7d-dade-4236-8772-ac2b775cbafa" />

Client will send the 1st message to KDS. It contains timestamp encrypted with Client key.

In 2nd message, AS-REP, TGT is encrypted with KDC key, which means the client cannot access this data. 

It also has TGS session key encrypted with Client Key, it means Client will access this data.

**2nd Flow:-**

<img width="766" height="240" alt="image" src="https://github.com/user-attachments/assets/0b2e37d1-4aaf-4ea9-963f-bb000aa9fd83" />

In 3rd message, the client will send TGT which is encrypted with KDC key (client cannot read this) to the KDC.

It also send Authenticator data to the KDC encrypted by TGS Session key. Client has received TGS Session key from KDC in the 2nd message. Client will be able to decrypt TGS Session key as it is encrypted via Client key.

In 4th message, the KDC received the Authenticator data, it will validate it and generates Service Ticket which will be encrypted via Service Key. The client cannot decrypt the ST. KDC will also send Service Session Key encrypted with TGS session key. Client can decrypt the TGS session key.

**3rd Flow:-**

<img width="800" height="222" alt="image" src="https://github.com/user-attachments/assets/ddc66e46-b7e4-4d06-8f7d-1da7cf936a86" />

In 5th message, the client will send ST and Authenticator data encrypted with Service session key to the Service. 

In 6th message, the service will decrypt the Service Ticket. It will get the service session key from the ST. With the help of service session key it will decrypt the Authenticator data, it will validate the Authenticator data with the Service Ticket and establish a session with the client.
